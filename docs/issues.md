# 已知问题与改进计划

记录实际使用中发现的问题，说明原因与拟采取的方案。原始记录保留在各条目的引用中。

**状态约定**：每个条目开头注明当前状态；修复后补记「修复」与「验证」，并保留原始现象与原因分析，便于回溯。后续新问题按同样格式追加编号，不要另建文档。

来源：用户于 2026-11-02 提交的 v0.2.0 使用反馈；第 3 条于 2026-11-05 追加。

## 1. 精准统计联动

**状态**：已修复（0.3.1，2026-11-06）。

**现状**：点击“精确统计”后，结果输出到右侧“查询”标签页，与地图点选的像元查询共用同一区域。

**期望**：统计结果应落在“属性”标签页中（当前属性栏的“已有统计”位置）；统计完成后自动切换到“属性”标签页并定位到该位置，给予短时高亮提示。“查询”标签页仅保留鼠标单击位置的网格属性，此行为保持不变。

**原因**：`geoquickview/app.py` 中 `statistics()` 与 `map_clicked()` 都把文本写入 `self.query_text`。

**方案方向**：统计结果改为写入属性树的统计节点；查询结果继续独占“查询”标签页。注意统计是全量计算，须保持后台执行与可取消。

**修复**：
- `statistics()` 完成后把结果写入当前图层的属性树节点「精确统计（全量，物理值）」，与「当前预览抽样值范围」一起置顶；切换波段/变量/切片或重新选择图层时该结果失效清除，避免把旧统计当成当前选择的结果。
- 统计完成自动切到“属性”标签页，滚动定位到该节点并高亮约 2.4 秒后恢复；`查询`标签页内容不再被统计覆盖。
- 统计仍使用受限后台线程池、进度条与“取消任务”，不写入源文件。

**验证**：`tests/gui_smoke.py` 断言统计完成后当前标签页为“属性”、统计节点存在且带高亮、`查询`标签页内容保持不变；“复制完整属性”与属性全文同样包含该统计节点。

## 2. 多图层预览卡住 / 可见性切换不即时

**状态**：已修复（0.3.1，2026-11-06）。

**现状**：同时添加多个 TIF 时，预览可能卡住，地图上一个都不显示；切换左侧图层可见性时响应滞后，看起来像“上方图层没生效、仍显示下方图层”（实际是上方图层仍在计算预览）。

**期望**：明确正在更新的图层状态；上层图层预览完成前不显示半成品，完成后一次性呈现。核心需求是“快速查看”，应优先保证首屏出图速度（精细数值交给“精确统计”，该操作不必快）。

**原因方向**（待验证）：
- 渲染任务串行执行，任一图层读取慢会阻塞整批（`render_scene()` 逐图层顺序渲染，共用一个 worker 池）。
- 每次视窗变化/可见性切换都会重新读取所有可见图层，没有缓存或取消已过期的渲染代次。
- 缺少“正在加载”的显式反馈，用户无法区分“还没好”和“没生效”。

**方案方向**：
- 每个图层独立渲染，完成后单独上屏，互不阻塞。
- 对过期代次提前取消（已有 `generation` 机制，需确认读取阶段也响应取消）。
- 未完成的图层显示占位/加载态，而不是上一代画面。
- 首屏优先读概览金字塔；缺少概览时按视窗降采样。

**修复**：
- 每个可见图层（以及省界底图）各占一个独立后台任务，线程池从 2 扩到 ≥4；先完成的图层立即上屏，不再等整批。
- 预览按「地图坐标系 + 视窗范围 + 波段/变量/切片」缓存到图层条目：视窗不变时切换可见性、调整顺序/透明度不再重新读取数据，只改变图层可见性，因此立即生效。
- 视窗或选择变化时，先取消上一代所有渲染任务再开始新一代；`data.render()` 及 GDAL/NC 读取、矢量遍历均检查取消标记，过期的结果按代次丢弃，不会覆盖新画面。
- 未完成的图层清除旧视窗画面，左侧图层条目标注「加载中…」，地图下方显示“正在加载 N 个图层：…”，完成后一次性呈现；失败原因也显示在同一位置。
- 首屏仍按当前视窗读取并限制到 1536 px 预览；有概览时由 GDAL 按读写窗口自动选择金字塔层，无概览时按视窗降采样，不读取全文件。

**验证**：`tests/gui_smoke.py` 用延迟注入证明慢图层不再阻塞快图层（快图层先出图时慢图层仍显示加载状态）；并断言视窗不变时勾选/取消勾选不会触发任何重新渲染。

## 3. nc数据加载后无法预览

**状态**：已修复（0.3.1，2026-11-06）。

**现状**：加载后显示“坐标不是均匀规则网格（或经度含重复端点）；可查看属性，不能按仿射栅格绘制”。对这种类型的 nc 数据做一定的适配，预览能显示出数据整体情况即可。

**原因**：`geoquickview/nc.py` 的 `_grid()` 要求经纬度为等间距一维坐标，且 0–360 经度在转换为 -180–180 后，360 与 0 变成重复端点，整条轴被判为不规则而拒绝绘制。

**修复**：
- 排序后合并重复的经度/纬度端点（例如 0–360 数据里的 360° 列），合并后的规则网格照常按仿射栅格预览；属性中注明“已合并重复的经度/纬度端点”。
- 一维坐标不完全等间距（拉伸纬度、不等间隔经度）时不再报错拒绘：按中点边界建立等间距预览轴，用最近邻把整体场映射到该轴上显示，保留全文范围与数值分布；属性中标注“非均匀网格：预览按等间距近似显示”。
- 像元查询、精确统计、切片标签仍使用原始坐标与原始像元，不受近似预览影响。
- 非均匀坐标的 NC 重投影会改变像元定位，因此明确拒绝并说明原因（预览、查询、统计仍可用）；规则网格及合并端点后的网格重投影行为不变。

**验证**：`tests/test_integration.py` 新增两项：重复经度端点（0–360 含 360）合并后预览、查询与属性标注正确；非均匀纬度网格可预览全范围、查询仍取原始像元、重投影给出明确拒绝。

## 4. 打包版加载示例数据报 “PROJ: Cannot find proj.db”

**状态**：已修复（0.3.2，2026-11-06）。

**现状**：0.3.1 便携包双击运行后点击“加载合成演示数据”，弹出“未能完成：RuntimeError: PROJ: proj_create_from_database: Cannot find proj.db”。示例数据在写入 GeoTIFF 坐标系时即失败；其它首次解析 EPSG 代码的操作同样受影响。

**原因**：PyInstaller 把 `proj_9.dll` 放在 `_internal\`，而 `proj.db` 被打包进 `_internal\Library\share\proj`；PROJ 按 DLL 所在位置推算数据目录（`_internal\..\share\proj`），因此找不到数据库。原逻辑依赖启动时把 PROJ 数据复制到可写的 ASCII 临时镜像并设置 `PROJ_DATA`；一旦临时目录不可写或复制失败，`PROJ_DATA` 为空，PROJ 回落到默认查找即失败。

**修复**：
- 打包后把 PROJ 数据移动到 `dist\GeoQuickView\share\proj`（与 `_internal` 同级），PROJ 按自身 DLL 的相对位置即可命中，不再依赖环境变量或可写临时目录。
- `geoquickview/__init__.py` 依次查找 `<bundle>\share\proj`、`<runtime>\Library\share\proj` 等位置；ASCII 路径直接使用，非 ASCII 路径继续复制到临时镜像作为后备。
- `scripts/build_windows.py` 打包后校验 `share\proj\proj.db` 存在；`scripts/verify_bundle.py` 解压后再断言该布局，防止后续改动破坏。

**验证**：新布局下把 TEMP/TMP/LOCALAPPDATA/USERPROFILE 指向不可用位置（无法生成 PROJ 镜像）仍能完成便携包 `--self-check`（栅格/NC/矢量、重投影、PNG/PDF 出图）；修复前同样条件会在 `create_samples` 的 `reference("EPSG:4326")` 处失败。
